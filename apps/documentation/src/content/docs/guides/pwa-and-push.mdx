# PWA and push notifications

Rösti's mobile access is the installable web app. iOS and Android store binaries stay on standby. See [Mobile store release](/lonestone-boilerplate/guides/mobile-store) for the later store plan. Do not start that work from this page.

Update this page as work lands. Tick a box in the same change that finishes the task.

## Decision

Ship one frontend, `apps/web-spa`, and let phones install it from the browser.

Use Web Push for notifications. The browser gives the API a push subscription. The API sends to that subscription with VAPID keys. There is no Firebase project and no Apple push key in this version.

Leave the Capacitor dependencies in the repo. Do not generate `ios/` or `android/`, and do not send the `ios` and `android` rows already stored in `device_token`.

Do not cache club, match, chat, or profile data in the service worker. The first version precaches the app shell only. Match data stays online.

## Already in the repo

- [x] Notification preferences, including `pushEnabled` and one flag per event
- [x] `device_token` table and `POST /api/notifications/devices` for `ios`, `android`, and `web`
- [x] Email delivery for new matches, RSVP reminders, cancellations, chat, and score reminders
- [x] A `deliver()` hook that reads push preferences and device rows, then only writes a log line
- [x] HTTPS in production: `https://rosti.lesk.fr` for the app and `https://rosti-api.lesk.fr` for the API

## Phase 1 — Installable app

Goal: a phone can add Rösti to the home screen and open it without the browser toolbar.

- [ ] Add `vite-plugin-pwa` in `injectManifest` mode, so the push handler is our code
- [ ] Add a web app manifest: name, short name, `standalone`, theme color, background color, and icons, including a maskable icon
- [ ] Link the manifest and the Apple web-app meta tags from `apps/web-spa/app/root.tsx`
- [ ] Precache the app shell and the hashed static files. Do not precache API responses
- [ ] Register the service worker in production builds. Keep it off during `pnpm dev` unless a task is explicitly testing push on localhost
- [ ] Stop Nginx from caching the service worker and the manifest for a year. `apps/web-spa/nginx.conf` currently caches every `.js` file that way. A stale worker would keep an old notification handler
- [ ] Replace the App Store and Play Store buttons on the invite screen with install instructions. Those buttons point at store listings that do not exist yet

On iPhone and iPad, installation is manual: Share, then Add to Home Screen. Chrome on Android can show an install prompt. Desktop Chrome can do the same. The app should explain the iOS steps. It should not pretend a button can install the app there.

## Phase 2 — Permission and subscription

Goal: a signed-in user can turn push on for the current browser, and turn it off again.

Ask for permission from the notification settings, after the user turns push on. Do not ask on the first page load. The current Capacitor bootstrap asks immediately. That path stays unused while the native apps are on standby.

- [ ] Show four states in the notification settings: off, not asked, allowed on this browser, and blocked by the browser
- [ ] When the user turns push on and the browser allows it, create a push subscription and send it to the API
- [ ] Store the Web Push endpoint, `p256dh` key, and `auth` secret. A single token string is not enough for Web Push
- [ ] Keep a per-browser installation id so logout removes this browser only
- [ ] Delete this browser's subscription on logout
- [ ] If the user blocks notifications, leave `pushEnabled` unchanged for their other browsers and show that this browser cannot register
- [ ] Expose only the public VAPID key to the SPA. The private key stays on the API

Account deletion already removes `device_token` rows through the user foreign key. Keep that cascade when the stored shape changes.

## Phase 3 — Sending

Goal: the events that already send email also send a push when the user allowed it.

The email copy and the push copy are different. A push carries a short title, a short body, the event type, `organizationId`, `matchId`, and the URL to open.

- [ ] Add a Web Push sender behind the existing `deliver()` method
- [ ] Send only to `web` subscriptions, and only when `pushEnabled` and the matching event flag are true
- [ ] Keep email. A push does not replace the email
- [ ] Delete a subscription when the push service says it is gone. Do not retry that subscription
- [ ] Log a temporary provider failure and continue. A failed push must not fail match creation, cancellation, or chat
- [ ] Skip stored `ios` and `android` tokens until the store plan resumes

Suggested payload:

```json
{
  "title": "Match on Thursday",
  "body": "Say if you are coming.",
  "event": "match_invite",
  "organizationId": "…",
  "matchId": "…",
  "url": "/matches/…"
}
```

The service worker displays `title` and `body`, and stores the rest on the notification. It does not call the API.

## Phase 4 — Opening the right match

Goal: tapping a notification opens the match, including when the app was closed.

- [ ] On `notificationclick`, focus an existing Rösti window or open one
- [ ] Navigate to the match URL from the payload
- [ ] Select the club from `organizationId` before loading the match. The open club may be a different one
- [ ] Ignore a payload that has no usable URL

iOS delivers Web Push only to a PWA that was added to the Home Screen, and only on iOS 16.4 or newer. Safari in a normal tab will not show these notifications. The settings screen needs to say that.

## Phase 5 — Production

Goal: one real phone receives a notification from production.

- [ ] Generate a VAPID key pair outside the repo
- [ ] Store the private key and the subject (`mailto:`) on the Dokploy `api` service
- [ ] Give the SPA the public key. A `VITE_` variable is acceptable for the public key only
- [ ] Confirm `https://rosti.lesk.fr` is the origin users install. Web Push is tied to that origin
- [ ] Install from Chrome on Android, turn push on, and receive a test notification
- [ ] Add the app to an iPhone Home Screen, turn push on, and receive a test notification
- [ ] Tap each notification from a closed app and from an already open app
- [ ] Log out and confirm that browser no longer receives pushes

There is no staging environment. Test against production with a real club account, or against localhost for the Chrome path.

## Risks

- iOS users who only open Safari, without adding the app to the Home Screen, will never receive a push.
- A browser that has blocked notifications will not show the permission prompt again. The screen must send the user to the browser settings.
- Caching `sw.js` for a year would freeze the notification handler. Phase 1 blocks on the Nginx exception.
- Chat notifications run inside the request that saves the message. The push call needs a short timeout so a slow push service does not hold that request.
- Changing the production hostname later invalidates installed apps and their subscriptions.
